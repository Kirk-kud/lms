01 · Product Vision
What We're Building

Love Inc LMS is a discipleship learning management system built specifically for university campus church communities in Ghana. It is not a generic LMS. It is a community platform — built for real people in a specific context.

The platform serves two roles: Tutors (spiritual mentors and leaders) who create and manage discipleship classes, and Students (university undergraduates at Ashesi, KNUST, UMaT, and Legon) who enrol, learn, submit work, and track their growth.

Unlike Canvas, Blackboard, or Moodle — which are built for academic institutions with thousands of courses and enterprise IT teams — this platform is built for a close-knit community. The design language, copy tone, and feature set are all intentional for that context. It should feel like community software, not course software.

The Design Principle
Students should never have to hunt for what they owe. Tutors should never have to leave the platform to understand what their class needs. Everything on this platform serves those two goals.

03 · Design Direction

04 · Competitive Research
What Canvas LMS Taught Us
Canvas holds 41% of the US higher-ed LMS market. Understanding what it gets right — and wrong — informed our roadmap directly.

Canvas won the market because of one structural bet: everything lives inside a hierarchy of Courses → Modules → Items, and the whole platform wraps around that spine. Every feature is either a way to put content into that structure or a way to surface it to students.

What Canvas Gets Right — and We Should Borrow
Feature What Canvas does Our gap Priority
Unified To-Do List A single cross-course feed of upcoming assignments, sorted by due date. Students never open each class individually. Students must navigate class-by-class to find what's due Phase 3
Announcement System Broadcast to entire class. Scheduled posting. Email triggered automatically. Separate from messaging. No way for tutors to communicate with their class at all Phase 1
SpeedGrader Split pane — student PDF left, grading panel right. Sequential student navigation. Audio/text comments. No downloading. Tutors see a file link only. No in-platform review or feedback. Phase 4
Module Prerequisites Lock Week 2 until Week 1 is complete. Configurable per-item completion type (view / mark done / score above X%). Modules are a flat, unordered list. No sequencing rules. Phase 5
Notification System Per-category, per-channel frequency settings. Email, SMS, push. All configurable per user. Students get no alerts when content or feedback is posted. Phase 2
Message Students Who From gradebook: one click to message "everyone who hasn't submitted" or "everyone below 60%". Targeted, contextual. No messaging system at all. Phase 6
What Canvas Gets Wrong — We Must NOT Copy
⚠
Course-to-course inconsistency
Canvas lets every instructor restructure their navigation. Students face a different UI per class. Our navigation is fixed, consistent, opinionated — and that stays.
⚠
The Inbox (buried messaging)
Canvas's internal messaging is too easy to miss. Students regularly miss important communications. If we build messaging, it must surface in the notification bell — not a separate system.
⚠
Two parallel quiz engines
Canvas shipped "New Quizzes" alongside "Classic Quizzes" for 5 years. Paralysis by technical debt. We never ship v2 of a feature without retiring v1.
⚠
Gradebook complexity
Canvas's gradebook is a full spreadsheet. Most tutors find it intimidating. Our scope stays simple — a grade and a comment per submission, not a weighted formula system.
The Core Insight
Canvas's #1 design principle is: students should never have to hunt for what they owe. Everything — the calendar, the To-Do list, the notifications — is just a different surface of the same answer to "what do I need to do today?" We adopted this principle as our own.
05 · Honest Assessment
Current Gaps & Issues
What the platform is missing, ranked by how much it hurts users right now.
Functional Gaps
—No announcements — tutors cannot communicate news to their class
—No notifications — students learn of new content only if they open the app
—No feedback loop — tutors cannot grade or respond to submitted work
—No module sequencing — students can skip ahead in the curriculum
—No password reset — forgotten passwords have no recovery path
—No way to unenrol a student from a class
UX & Polish
—Student dashboard pulls stats from all classes — no per-class breakdown
—Empty state coverage unverified for edge cases (zero classes, zero submissions)
—Video module items cannot be previewed in-browser — just an external link
—Current UI lacks personality and community feel — too generic
—No mobile optimisation verified — sidebar layout breaks on small screens
Infrastructure
—No CI/CD — deployment to Render and Vercel is fully manual
—No automated tests on the web side (Jest exists in API only)
—No error monitoring (no Sentry or equivalent)
—No analytics — no visibility into feature usage or engagement patterns

06 · Implementation Roadmap
The Next 6 Phases
Each phase is independently shippable. Stop anywhere and the system is coherent and useful.
1
Announcements
Tutors have no way to communicate with their class. Students have no idea when something important changes, unless they open the app and happen to look.
DB: New announcements table (id, class_id, tutor_id, title, body, scheduled_at, created_at)
API: POST, GET, PATCH, DELETE — tutors see all including drafts; students see only published
Web (Tutor): New "Announcements" tab in class nav; create/edit modal with optional scheduled date picker
Web (Student): Read-only chronological list; unread dot for announcements since last visit
Low effort New DB table New API module 2 new UI tabs
2
In-App Notification Bell
Announcements are useless if nobody sees them. This phase adds the platform-level alerting backbone that every future phase hooks into.
DB: New notifications table (id, user_id, type enum, title, body, resource_type, resource_id, read, created_at)
API: GET /notifications, PATCH read, PATCH read-all — no user-facing create; other services trigger internally
Web (Both): Bell icon in Topbar with unread badge; dropdown with notification list; click → navigate to resource + mark read
Triggers: New announcement → enrolled students notified. New assignment → enrolled students. New module → enrolled students.
Medium effort New DB table Topbar component change Internal service hooks
3
Unified Student Dashboard — To-Do
Students must open each class individually to discover what they owe. This is the #1 friction Canvas eliminated — a single view of all upcoming work.
DB: No schema changes — data exists across assignments, submissions, and enrollments
API: New GET /students/me/todo (all assignments across enrolled classes, with submission status, sorted by due date). New GET /students/me/summary (aggregate stats)
Web (Student): Dashboard redesign — stat cards from summary endpoint; To-Do list with filter tabs (All / Upcoming / Overdue / Submitted); recent announcements sidebar
Medium effort No schema changes 2 new API endpoints Dashboard page redesign
4
Submission Feedback & Inline Review
Tutors can see who submitted but cannot review or respond to work. Students submit into a void. This closes the most important pedagogical gap in the platform.
DB: Add to submissions: feedback (text), grade (text), feedback_at (timestamp), grade_released (boolean)
API: PATCH /assignments/:id/submissions/:id/feedback — tutor writes grade + feedback, toggles release; triggers student notification on release
Web (Tutor): Split-pane review panel — student PDF inline (iframe), grade input + feedback textarea + release toggle, Prev/Next student navigation
Web (Student): Feedback section appears on submitted assignment when released; "Awaiting feedback" neutral state when not yet released
High effort Schema migration New API endpoint SpeedGrader UI Hooks Phase 2
5
Module Sequencing & Gating
Modules are a flat, unordered list. Tutors cannot enforce a curriculum path. Students can skip to Week 8 without completing Week 1.
DB: Add prerequisite_module_id to modules; new module_item_completions and module_completions tables
API: POST /modules/items/:id/complete; GET /modules/class/:id updated to return per-student completion state; POST /modules/class/:id/reorder
Web (Tutor): Drag/reorder handles; prerequisite dropdown in module edit modal; per-item completion toggle
Web (Student): Locked module state with padlock + unlock condition; Mark as complete button; per-module progress bar
Medium effort 2 new DB tables 3 new API endpoints Module UI updates
6
Targeted Messaging ("Message Students Who")
Tutors want to nudge specific students — those who haven't submitted, those with low attendance — without manually picking through the roster. This is the Canvas "Message Students Who" pattern.
DB: New messages and message_recipients tables; filter_type enum (all, not_submitted, low_attendance, manual)
API: POST /classes/:id/messages — resolves filter → recipient list → notification per student → logs to messages; GET /classes/:id/messages
Web (Tutor): "Message students" button on Roster page with filter selector; "Message who hasn't submitted" one-click from assignment submissions page
Web (Student): Receives as bell notification (Phase 2). No reply in v1.
Medium effort 2 new DB tables Depends on Phase 2 2 tutor entry points
07 · Sequencing & Next Steps
How to Ship This
The rationale behind the phase order — why each phase unlocks the next.
1
Announcements — First real tutor→class communication
Standalone. No dependencies. Ships fastest. Immediately useful. Every class needs this from day one.
2
Notification Bell — The backbone for everything that follows
Announcements are useless if students don't see them. Build the alerting infrastructure now. Phases 4 and 6 both hook into this system — it must exist first.
3
Unified To-Do — Biggest student UX win, lowest risk
No schema changes. One new API endpoint. High impact for students. Ships fast and proves the new dashboard design direction.
4
Submission Feedback — Closes the grading loop
Shifts the platform from "submit and forget" to an actual pedagogical cycle. Students need to know their work matters. Hooks into Phase 2 for grade-release notification.
5
Module Gating — Adds curriculum structure
Depends on modules working well (they do). Adds new tables but doesn't touch existing data. Tutors can now build a true learning journey, not just a file list.
6
Targeted Messaging — Most valuable once engagement data exists
Last because it depends on Phase 2 (notification delivery) and is most powerful when tutors have real submission and attendance data to filter against.
Immediate Next Steps
1. Approve the UI direction — review the prototype and sign off on the design system before any implementation begins.
2. Begin Phase 1 — Announcements. Database migration, NestJS module, two new UI tabs. Estimated: 1–2 days.
3. Phase 2 immediately after — Notification Bell. The backbone. Without it, Phase 1 doesn't reach its full value.
4. Apply the new design system — the UI redesign should be applied alongside Phase 1–3, not as a separate project.
